# NAS 软件开发与部署

把需求落实为已验证的代码、Git 提交和可核验的 NAS 服务；按用户本次授权决定执行哪些阶段。只制作方案、skill 或文档时，不因此部署应用；只部署既有版本时，不另行扩展功能。

## 连接与项目定位

- 当前个人 NAS 使用本机私密连接档案 `~/.codex/private/nas/evantra.json`。先检查文件是否存在，不输出其内容。实际连接地址、用户、端口和凭据均由该档案提供，不能从公开示例猜测密码。
- 使用 [scripts/nas.py](scripts/nas.py) 连接：`python3 <skill-dir>/scripts/nas.py check`。它检查已知主机密钥，从档案或指定 SSH 私钥认证，并通过终端输入密码，不把密码放入命令参数。
- 当前工作区为 DesignBoard 时，读取 [references/designboard.md](references/designboard.md)；连接失败、迁移项目或设置私密档案时，读取 [references/connection.md](references/connection.md)。
- 密码认证失败一次就停止重复尝试。如果用户要求查找旧聊天，先用应用的聊天检索工具定位最近成功部署记录和**之后更新的用户凭据**，不要只重试本聊天最早的密码。不可用时说明真实错误并索取当前连接方式。

## 开发、验证与同步

1. 阅读仓库 `AGENTS.md`，检查 Git 状态和现有运行方式。保留其他任务的修改，不整批提交整个工作区。
2. 先复现并定位问题，再沿用项目现有技术栈实现。区分接口失败、会话失效、前端交互和缓存问题；不能仅凭页面截图判定根因。
3. 跑与变更对应的测试；涉及保存、登录或导航时验证完整路径：用户操作 → API → 持久化 → 页面反馈。浏览器验证使用隔离数据，不覆盖用户白板。缺少 npm 时可用可用的 Node 执行 `package.json` 中列出的测试入口，维持所需的串行顺序。
4. 按仓库约定只提交本任务文件，推送配置的 Git 远端，核对远端提交。Git 失败要如实报告；不能把本地提交称为已同步。部署文件应来自已测试的提交，不能夹带其他任务未提交的修改。

## 部署与回滚

仅在本次工作包含部署且有可用连接时执行。详细操作模板见 [references/deployment.md](references/deployment.md)。

- 上线前确认目标目录、Compose 项目、目标服务、当前挂载和公网入口，不能凭上一轮记忆修改其他应用。
- 保留生产 `.env`、`compose.override.yaml`、`secure/`、证书卷和业务数据卷。更新源文件不能覆盖这些文件。先备份目标程序、保存旧镜像标签，并备份/校验受影响的数据；有持续写入的应用使用其一致性备份方式。
- 用 [scripts/package_runtime.py](scripts/package_runtime.py) 从明确提交打包显式指定的运行时路径；脚本拒绝已知私密目录，排除未跟踪和未提交内容。新增静态模块时核对服务端白名单和 Docker `COPY`。
- 构建并只重建需要更新的服务，默认不触碰 HTTPS 网关。避免 `down -v`、清卷、全局镜像清理、强推或修改 NAS 全局 Docker 配置。首次部署的新项目先检查端口冲突，再建立独立目录、Compose 项目和数据卷。
- 构建失败时保留运行中的版本。启动或健康检查失败时，按本次备份恢复目标程序和旧镜像；不擅自恢复数据备份覆盖上线后新写入的数据。一次回滚仍失败就保留日志，说明阻碍，不无限重试。
- 完成后验证容器健康、外部 HTTPS/证书、认证保护、变更资源与提交一致及对应用户流程。静态文件响应 200 不等于功能已验证；只验证了 API 时说明浏览器验证的限制。数据校验差异须先区分用户并发编辑与程序影响。
- 交付实际访问地址、提交号、验证结果和重要限制；部署受阻时明确区分“代码已推送”和“NAS 已上线”。后端重启可能撤销会话，提示重新登录；存在未保存内容时先保护数据再刷新。

## 凭据边界

连接档案和密码只存本机私密目录，不复制进此 skill、项目仓库、部署包、截图或报告。私钥留在本机；验证凭据时不输出原文。此 skill 不授予超出用户本次请求的发布、账号变更或网络开放权限。
