# SVG 先行界面开发

把 SVG 用作可预览、可修改的视觉约定，收敛布局和状态后再映射为真实 UI。SVG 是设计中间表示，是否作为运行时资源取决于目标框架。

## 先判断是否适用

- 先查看项目现有界面、框架、组件、字体和资源约束。已有批准的 Figma、截图或组件规范时，以它们为准；只有需要澄清的部分才增加 SVG 草图。
- 用户要快速实现一个简单修改时，不额外制造完整设计阶段。布局尚未确定、原生控件难以描述或游戏界面层次复杂时，SVG 最有价值。
- 初稿可根据现有上下文推进；会影响技术栈、资源授权或产品行为的缺失信息需要澄清。不要把设计稿确认解释为发布或外部写入授权。

## 产出可交流的设计稿

1. 确定画布尺寸、主要任务、信息优先级和本轮涉及的状态。把参考尺寸与响应式规则区分开。
2. 用 SVG 绘制具体布局，复用现有色彩、间距、文字层级和组件。用语义化 `id` / `<g>` 组织区域，用 `<defs>` 复用符号、渐变等；文字尽量保留为 `<text>`，图片引用使用稳定的相对路径或便携的内嵌数据。
3. 对游戏界面，将背景、人物或物体、交互 HUD、浮层分组。需要独立交付时导出透明图层并说明锚点和叠放顺序；不要为了分层而把每个图形都拆成文件。
4. 展示正常态和影响实现的重要状态，例如悬停、按下、选中、禁用、空态。拖拽、滚动、视差、动画用状态说明或可运行原型补充；静态 SVG 无法证明交互正确。
5. 渲染查看 SVG，检查字体回退、裁剪、遮挡、对比度和资源缺失。让用户看到实际设计稿。若用户已授权自动完成，依据现有约束和渲染结果迭代，不反复要求确认。

## 收敛后实现

- 指定一份设计稿作为本轮参照，避免一边改稿一边无边界改代码。
- 把视觉区域映射到现有组件、布局容器和交互状态；明确固定、拉伸、滚动和锚定规则。将字体、颜色、间距等映射到现有设计令牌。
- 简单形状、规则边框等可用目标框架绘制；角色、纹理等图像继续使用合适的位图资源。只有在平台支持且合适时直接使用 SVG。
- 以项目技术栈实现，保留真实文本、事件、焦点、键盘操作和无障碍语义。SVG 中的 `<text>`、按钮图形或 `id` 不会自动变成可访问的控件。
- 不把整页截图当成可交互页面交付，不为实现设计稿而更换用户的技术栈。

## 对照修正与交付

在相同视口渲染设计稿与实现，优先修正整体布局、信息层级、尺寸和字体，再处理装饰。对重要状态及至少一个有代表性的不同尺寸进行验证；有性能要求时验证实际目标设备。说明已验证与未验证的行为。

交付设计源文件、必要资源、真实实现、简短映射说明和验证结果。用户尚未要求代码时，只交付设计与实现建议。视觉接近不能推导出逻辑、性能或架构正确；保留自动化检查与行为验证。
